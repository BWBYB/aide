## 0. 三十秒版本

我在做一个「学习 + 求职」双轨的个人 Agent。它的设计不是先写代码再补文档，而是反过来：

**先按书稿第 1 章的公式把系统拆成 6 个格子，再给每个格子写一份带拒绝条件的验收清单，最后才动代码。**

一晚上把 M0 推到「待验收」，过程中发现并修复了上游依赖里一个**会静默污染所有检索结论**的向量池化缺陷。修复后同一批题的数字从 `0.0000` 回到 `0.9333`，也让我推翻了自己一小时前刚写下的结论。

面试里我会讲三件事：

1. **Agent 的竞争力在 Harness，不在模型。** 我把「约束 / 验证 / 纠正」当成有代码落点的一等公民，而不是提示词里的一句话。
2. **「完成」由验证器判定，不由模型自述。** 全项目 9 个里程碑，AI 只能推进到「待验收」，勾选权在用户手里。
3. **一个数字的意义取决于它的测量条件。** 我撤回过自己的一版评估结论，原因是尺子量错了对象。

## 2. 方法论：不是「参考了书」，而是「可追溯地引用书」

### 2.1 22 个 skill 的账要对得上

书仓库配了 22 个 skill，我把它们的去向逐个交代清楚，而不是「都用上了」：

| 去向 | 数量 | 说明 |
|---|---|---|
| 按里程碑使用 | 16 | M0–M6 每个阶段加载对应 skill，结论写进验收清单 |
| 备选 | 1 | `knowledge-org`（结构化索引）：当前 567 chunks 用不上，等 recall 长期上不去再启用 |
| 明确不做 | 5 | `computer-use`、`post-training-strategy`、`reward-design`、`bad-case-to-dpo`、`multi-agent-design` |

「不做」必须给理由，不能含糊过去。例如不做多 Agent 的依据是书稿第 10 章的判据：**多 Agent 只有在引入单 Agent 拿不到的新信息时才成立**，所以等 M5 证明单 Agent 不足再立项。

### 2.2 每份验收清单固定五段

```
1. 命令        —— 可复制执行，附成功与失败两种预期输出
2. 自动检查    —— 必须绿的测试，贴真实输出，不接受口述
3. 人工判断    —— 程序验不了的 1–3 项，需要人亲自看
4. Skill 留痕  —— 加载了哪些 skill、采纳哪条结论、冲突如何裁决（空着即未完成）
5. 拒绝条件    —— 明确哪些情况算不通过
```

第 5 段是整个体系里最有用的一段。举几个真实写下的拒绝条件：

- 「报告中出现『提升 X%』却没有置信区间或配对分析」
- 「模型自称完成即退出，未经过验证器」
- 「压缩后丢失原始轨迹指针，无法回溯」
- 「用 4/4 通过写成『系统 100% 可靠』」

### 2.3 状态机只有人能动最后一步

```
pending → in_progress → 待验收 →（用户勾选）→ 完成
```

AI 维护前三个状态，**只有用户能把状态改成「完成」**。这条规则在 `AGENTS.md` 第三节，违反即视为未完成。

## 3. 架构：六个格子

书稿第 1 章给了全项目唯一的分层依据：

```
Agent = LLM + 上下文 + 工具
生产形态：Agent = Model + Harness
Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正
```

| 格子 | 落点（目标态） | 对应里程碑 |
|---|---|---|
| LLM | `src/aide/llm/` provider 抽象 + 跨厂商接管 | M1 |
| 上下文 | 上下文装配、状态栏、压缩、记忆、知识层 | M0 / M1 / M3 |
| 工具 | 工具协议（先于工具实现）、MCP、主动发现 | M2 |
| 约束 | 主循环、三重闸门、权限策略 | M1 / M2 |

| 纠正 | 故障恢复 + 进化闭环 | M1 / M6 |

> 诚实的现状：**只有 `knowledge/` 已实现**，`src/aide/`、`web/` 都还不存在。架构文档顶部已加状态行，避免后续接手的编码 Agent 把目标态当现状。

四个贯穿全书的设计模式，我都落了具体的验收锚点：

| 模式 | 在本项目的落点 |
|---|---|
| 提议者—审核者 | 本项目的审查环节（见第 6 节）；M5/M6 的判官与验证器分离 |
| 渐进式披露 | M2 的 `discover_tools` 两级路由；技能元数据常驻、正文按需 |
| 只增不改 | 上下文静态前缀字节稳定；状态栏只追加在末尾 |
| 边界集 + 保留集 | M6 进化门禁：改一次要在「应当变」和「不应当影响」两批样本上同时验证 |

## 5. M0 实操全过程（本文核心）

### 5.1 为什么先做知识层

书稿第 2 章的核心论断是「上下文决定能力上限」。而当时的索引只有 5 份文档 181 个 chunk，**chapter4–10 全不在库内**——工具、评估、进化、多 Agent 的方法论恰好在那 7 章里。所以要做的第一件事不是写循环，是把知识层撑起来。

### 5.2 首轮：所有配置全线下滑

语料从 5 文件 181 chunks 扩到 24 文件 567 chunks（书稿 12 文件 547 + 个人资料 12 文件 20），Dense 构建 192.2s。在旧 21 题冻结集上重跑 E0–E4：

| | E0 裸 dense | E1 BM25 | E2 +RRF | E3 +重排 | E4 +改写 |
|---|---|---|---|---|---|
| 首轮 v2（带缺陷索引） | 0.4762 | 0.6667 | 0.6190 | 0.7619 | 0.8571 |

当时的解释是「扩容必然带来召回稀释」——语料变大、IDF 变了、候选竞争者变多。这个解释**听起来完全合理**，我差点就把它写进了结论。

### 5.3 转折：不是题太难，是索引坏了

按 M0 验收清单的最后一段「本步的诚实点」——**拿 v1 数字当 v2 结论就是本轮最典型的夸海口**——我没有直接接受那个解释，而是去验证一个更基本的问题：索引里的向量，和它自己的文本还对不对得上？

对同一段 `embedding_text` 重新编码，与索引中存的向量求余弦：

| chunk | 自相似度 | 应得 |
|---|---|---|
| `book/chapter7.md#30` | 1.000 | 1.000 ✓ |
| `book/afterword.md#0` | 0.274 | 1.000 ✗ |
| `book/chapter3.md#29` | 0.205 | 1.000 ✗ |
| `personal/knowledge/profile.md#0` | **0.001** | 1.000 ✗ |

同一段文本与自己比，有的 1.0，有的接近 0。**向量与文本部分错位**——这不是「题难」，是索引坏了。

外部症状也吻合：用「吴禹的求职方向」检索个人资料，正确 chunk 连 Top-8 都进不去，最高分只有 0.37；新建的 15 题集上 E0 Hit@5 = **0.0000**，8 道 fact 题全灭。

### 5.4 根因：池化方式与 padding 方向不匹配

上游 `agentbook_rag/embedding.py`：

```python
def _last_token_pool(last_hidden_state, attention_mask):
    sequence_lengths = attention_mask.sum(dim=1) - 1   # 只对 right padding 成立
    return last_hidden_state[batch_indices, sequence_lengths]
```

而同文件的 `QwenEmbedder.__init__` 明确用：

```python
AutoTokenizer.from_pretrained(model_name, padding_side="left")
```

**left padding 下，真实 token 在序列末尾，`sum()-1` 指向的是 padding 区。** 短文本取到 pad 位置的隐状态，向量与文本就此脱钩。

为什么 v1 没暴露：`chunk_markdown` 用固定 512 token 窗口，中间块几乎都满。**一个 batch 里 8 条长度全相同时不产生 padding，`sum()-1` 恰好等于末位，结果是对的。** 只有文件尾块和短文档（个人资料全部属于此类）会触发。181 个 chunk 里这类占比很低，所以 v1 的评估数字看起来一直「正常」，问题被掩盖了两周。

这个 bug 的性质很关键：**它是静默的**。不报错、不崩溃，只是让一部分向量悄悄变成噪声，然后所有基于检索的结论一起失真。

### 5.5 修复：不改上游，运行时覆盖

上游是只读的（AGENTS.md 第二条），所以在 `knowledge/loader.py` 里导入后覆盖模块级函数：

```python
def _left_padded_last_token_pool(last_hidden_state, attention_mask):
    return last_hidden_state[:, -1]

legacy._last_token_pool = _left_padded_last_token_pool
```

生效原理要说清楚：`embedding.py` 里是 `pooled = _last_token_pool(...)` 这样的**模块内名字查找**，所以替换模块属性可以改到；如果上游写的是 `from .pooling import _last_token_pool`，这个补丁就会失效。

被否决的三个方案记在 ADR 0002：

| 方案 | 否决理由 |
|---|---|
| 改旧包源码 | 违反「上游只读」约束 |
| `batch_size=1` 回避 padding | 能绕开但慢数倍，且没修根因，换模型还会复发 |
| 只调整题目 | 等于把索引缺陷合理化，会让后续所有结论失真 |

另外确认了一件事：**query 侧不受影响**。`encode_query` 是单条 `_encode([prompt])`，batch=1 不产生 padding，`sum()-1` 恰好是末位。所以缺陷只存在于文档侧。

### 5.6 重测与口径修正

修复后用新代码重建 corpus-v2 索引，两套题集：

| 21 题（ch1–3） | E0 | E1 | E2 | E3 | E4 |
|---|---|---|---|---|---|
| 修复前 | 0.4762 | 0.6667 | 0.6190 | 0.7619 | 0.8571 |
| 修复后 | **0.9524** | 0.6667 | 0.8571 | **0.9048** | 0.9048 |

| 15 题（ch4–10 + 个人资料） | E0 | E1 | E2 | E3 | E4 |
|---|---|---|---|---|---|
| 修复前 | 0.0000 | 0.0667 | 0.0000 | 0.0667 | 0.0667 |
| 修复后 | **0.9333** | 0.8000 | **1.0000** | 0.9333 | 0.9333 |

然后是**口径**，这一步比数字重要：

- 21 题上 E3 命中 18→19，improved 2 / degraded 1，discordant=3，McNemar 精确检验 **p = 1.0**。
- 所以正确表述是「**未观察到超出噪声的变化**」，不能写成「扩容提升/降低了检索能力」。
- 同时必须标混杂：**v1 基线是在带缺陷的旧索引上测的，v2 已修复，两列差值 = 扩容效应 + 修 bug 效应，不能归因到单一变量。**

我撤回了首轮「全线下滑 9–19 个点」的结论，并在 `docs/status.md` 里写明「第一轮数字作废」。这是整个项目里我最愿意拿来讲的一次自我否决。

### 5.7 修复后浮现的新问题（尚未解决）

修复后出现一个反直觉结果，21 题上：

```
E0 裸 dense 0.9524  >  E3 加重排 0.9048  >  E2 加融合 0.8571
```

**加工越多越差**，最大损失发生在融合环节（−9.5 点），不在重排环节。BM25 的 Hit@5 只有 0.6667，等权 RRF 把 0.9524 拉了下来。

而 15 题上结论相反：`E2 1.0000 > E0 0.9333`，融合是正增益。

**两套题集给出相反结论**，且各自只有 15 / 21 题，都判不了。这直接决定了下一步不是调参，而是先合并题集（见第 8 节）。

### 5.8 测试分层

M0 的测试刻意分成两档，代价是「快的很快、慢的很脆」：

| 测试 | 对应验收项 | 特点 |
|---|---|---|
| `test_corpus_manifest_has_all_book_files` | manifest 覆盖 12 个书稿文件，且 `reference-answers.md` 必须被排除 | 快 |
| `test_personal_chunks_use_personal_prefix` | 个人资料走 `personal/` 前缀，不混进 `book/` | 快 |
| `test_manifest_records_sha256` | 每个源文件都有哈希，可复核语料未被篡改 | 快 |
| `test_chunk_ids_stable_for_old_files` | ch1–3 的 `file#index` 与 v1 完全一致，旧题集 gold 才可复用 | 快 |
| `test_expand_keeps_unknown_variable_literal` | `${VAR}` 未设置时保持字面量，不被悄悄展开成空串 | 快 |
| `test_embeddings_self_consistent` | 抽样 chunk 的自相似度 > 0.999 | **慢**，需加载嵌入模型，默认跳过 |

快测 5 条跑完 **0.06 秒**，慢测单独 35 秒且依赖模型下载。

清单里还写了一种「失败预期」——故意给不存在的路径：

```bash
AIDE_RAG_HOME=/tmp/not-exist make corpus
# 预期：明确报「AIDE_RAG_HOME 不存在」并非零退出，不得抛栈
```

这是把错误处理也纳入验收：**一个只会成功、不会优雅失败的脚本，不算写完。**

但这里留了一个真实的教训（见第 8 节第 2 条）：慢测默认关闭、且启用后要联网，等于**这个 bug 的守卫和这个 bug 一样静默**。正确做法是把校验放进构建流程，让模型在内存时顺手算掉。

## 7. 关键取舍（面试可直接引用）

| # | 取舍 | 被否决的方案 | 依据 |
|---|---|---|---|
| 1 | 知识层用适配器桥接，不迁移旧包 | 复制进新仓库（两份真相）/ 重写检索层 | 旧包 37 个测试与冻结基线零影响 |
| 2 | 上下文布局固定为「静态前缀 + 轨迹 + 尾部状态栏」 | 状态栏写进系统提示词 / 每轮重排消息顺序 | 前缀越稳定缓存命中越高 |
| 3 | 工具协议先于工具实现 | 先写 16 个工具再抽协议 | 否则 MCP 会开出第二条执行路径 |
| 4 | 记忆用「卡片 + 分层」，不用纯向量堆叠 | 全量对话向量化 / 只存最新值 | 个人场景「记错」比「记不住」更致命 |
| 5 | 验证器优先于判官 | 全部 LLM-as-Judge | 否则分不清「真提升」与「判官偏好漂移」 |
| 6 | 进化只改可回滚载体 | 直接微调模型 | prompt/skill/程序可 diff、可灰度、可回滚 |
| 7 | 单机优先 | 上 Postgres/Redis/K8s | 会让「能跑通」变成「能部署」，拖垮进度 |

## 8. 还没解决的（诚实清单）

按优先级：

## 9. 面试问答预案

**Q：你怎么保证 Agent 不吹牛？**
A：三层。①运行时——「完成」必须由验证器判定，模型自称完成不算；②流程上——9 个里程碑只有用户能勾「完成」，AI 最高只能推到「待验收」；③我自己就是例子：首轮评估结论我写下了，一小时后自己推翻，因为它量错了对象。

**Q：你怎么知道一次改动是有效而不是噪声？**
A：单变量 + 配对检验 + 明示混杂。M0 的 21 题上，E3 命中 18→19，翻转 3 题，McNemar p=1.0，所以结论只能写「未观察到超出噪声的变化」。另外 v1 基线跑在带缺陷的索引上，所以两列差值 = 扩容 + 修 bug，不能归因单一变量——这句我写在报告顶部，不是脚注。

**Q：这个项目里最有价值的技术发现是什么？**
A：一个静默的语义 bug。上游用 `attention_mask.sum()-1` 定位末 token，但 tokenizer 是 left padding，短文本取到 pad 位置的隐状态。它不报错、不崩溃，只在 batch 内长度不齐时把一部分向量变成噪声。发现它的方法很土：拿一段文本和它自己的向量求余弦，应该是 1.0。

**Q：为什么不用 LangChain / 现成 Agent 框架？**
A：因为这个项目要展示的正是 Harness 层。框架会把约束、验证、纠正藏在内部，我讲不出「为什么这样设计」。自己写的话，每个决策都能指向一个具体的验收断言。

**Q：为什么不做多 Agent？**
A：书稿第 10 章的判据是「多 Agent 只有在引入单 Agent 拿不到的新信息时才成立」。我还没有单 Agent 不足的证据，先做就是拿成本换热闹。等 M5 的任务层评估给出数据再立项。

**Q：这 9 个里程碑你只完成了 1 个，怎么说明能力？**
A：M0 里包含一次完整的「提出假设—测量—发现异常—定位根因—修复—重新测量—修正口径」闭环，这个闭环的难度不在代码量。另外九份验收清单是我对未来八个模块的设计判断，每份都写了拒绝条件——这部分现在就可以被审。
