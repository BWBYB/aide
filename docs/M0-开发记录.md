## 1. 起点：为什么先做知识层

原索引只有 5 份文档、181 chunks，**chapter4–10 全不在库内**。而工具（ch4）、Coding Agent（ch5）、交互（ch6）、评估（ch7）、后训练（ch8）、进化（ch9）、多 Agent（ch10）的方法论恰好在那 7 章里——M1 到 M8 每一步都要通过检索取方法论。

所以 M0 不是"顺手把书塞进向量库"，是给后面八个里程碑铺数据层。

知识层不走重写，只走适配器桥接（ADR 0001）：旧包没有 `pyproject.toml`，不能被声明为 PEP 508 依赖，通过 `AIDE_RAG_HOME` 注入 `sys.path`；收益是旧包 37 个测试与既有评估基线零影响。

| 分块 | 512 token / 64 overlap（12.5%） | 落在 skill 给的 256–1024 / 10–20% 区间内；与 v1 同参数，保证"扩容"是单变量 |

| 融合 | RRF k=60 | 沿用旧包 |
| 重排 | `BAAI/bge-reranker-v2-m3`，candidate-k=20 | 沿用旧包默认 |
| 耗时 | 192.2s（首次加载模型） | — |

语料构成：

```
book/       12 文件  547 chunks   （chapter1–10 + introduction + afterword）
personal/   12 文件   20 chunks
合计        24 文件  567 chunks
```

两个关键决定：

1. **排除 `reference-answers.md`。** 参考答案进检索库等于数据泄漏——评测时模型能检索到答案本身。`corpus.yaml` 里显式列进 `excluded`，测试里专门断言它不在库内。
2. **每个源文件记 sha256。** 写进 `manifest.json`，可复核语料未被篡改；这也是后来"上游未被修改"的取证基础。

产物结构：

```

├── dense/{chunks.jsonl, embeddings.npy, manifest.json}
├── bm25/{chunks.jsonl, tokens.jsonl, manifest.json}
└── manifest.json          # 24 个文件的 sha256 / chunks / chars
```

## 4. 阶段三 · 转折：先验索引，再解释数字（约 19:00）

M0 验收清单最后一段是自己写的"诚实点"：

> 本步的产出不是"更高的分数"，而是"同样的问题集在新语料上重新测了一遍，漂移了多少、为什么"。拿 v1 数字当 v2 结论，就是本轮最典型的夸海口。

这句话逼出了一个更基础的问题：**索引里的向量，和它自己的文本还对得上吗？**

对同一段 `embedding_text` 重新编码，与索引中存的向量求余弦：

| chunk | 自相似度 | 应得 |
|---|---|---|
| `book/chapter7.md#30` | 1.000 | ✓ |
| `book/afterword.md#0` | 0.274 | ✗ |
| `book/chapter3.md#29` | 0.205 | ✗ |
| `personal/knowledge/profile.md#0` | **0.001** | ✗ |

同一段文本与自己比应当是 1.0。出现 0.001 说明**向量与文本完全错位**，不是"题难"。

外部症状吻合：用「吴禹的求职方向」检索个人资料，正确 chunk 连 Top-8 都进不去，最高分只有 0.37。

## 5. 阶段四 · 根因与修复（19:12–19:24）

根因在旧包 `agentbook_rag/embedding.py`：

```python
def _last_token_pool(last_hidden_state, attention_mask):
    sequence_lengths = attention_mask.sum(dim=1) - 1   # 只对 right padding 成立
    return last_hidden_state[batch_indices, sequence_lengths]
```

而同文件构造 tokenizer 时写的是 `padding_side="left"`。

**left padding 下真实 token 在序列末尾，`sum()-1` 指向的是 padding 区。** 精确触发条件不是"尾块/短文档"，而是：

> **一个块只要在它所在的那个 batch 里不是最长，就会被 pad，就会取错。**

v1 之所以"看起来正常"，是因为 512 窗口下大量中间块是满的，一个 batch 里 8 条等长时不产生 padding，`sum()-1` 恰好等于末位。

修复遵守"上游只读"（AGENTS.md 第二条）：在 `knowledge/loader.py` 里运行时覆盖模块级函数：

```python
def _left_padded_last_token_pool(last_hidden_state, attention_mask):
    if int(attention_mask[:, -1].sum()) != attention_mask.shape[0]:
        raise ValueError("末位不是真实 token，上游可能改回 right padding")
    return last_hidden_state[:, -1]

legacy._last_token_pool = _left_padded_last_token_pool
```

生效原理：上游是 `pooled = _last_token_pool(...)` 的模块内名字查找，所以替换模块属性有效；若上游写成 `from .pooling import _last_token_pool`，补丁会失效。

被否决的三个方案记在 ADR 0002：改旧包源码（违反只读）、`batch_size=1` 回避（慢数倍且不修根因）、只调整题目（把缺陷合理化）。

同时确认 query 侧不受影响：`encode_query` 是单条 `_encode([prompt])`，batch=1 不产生 padding，`sum()-1` 恰好是末位。

|---|---|---|---|---|---|
| 修复前 | 0.4762 | 0.6667 | 0.6190 | 0.7619 | 0.8571 |
| 修复后 | **0.9524** | 0.6667 | 0.8571 | **0.9048** | 0.9048 |

| 15 题（ch4–10 + 个人资料） | E0 | E1 | E2 | E3 | E4 |
|---|---|---|---|---|---|

| 修复后 | 0.9333 | 0.8000 | **1.0000** | 0.9333 | 0.9333 |

口径修正（比数字重要）：

- 21 题上 E3 命中 18→19，improved 2 / degraded 1，discordant=3，**McNemar 精确检验 p = 1.0**。
- 正确表述是「**未观察到超出噪声的变化**」，不是"扩容提升/降低了检索能力"。
- 必须标混杂：v1 基线跑在带缺陷的索引上，v2 已修复，**两列差值 = 扩容效应 + 修 bug 效应，不能归因单一变量**。

## 7. 阶段六 · 题集扩充与合并（19:10–20:19）

第一轮审查指出：21 题的 gold 只覆盖 `chapter1/2/3`，**新增的 ch4–10 与个人资料零题**——尺子测不到 M0 的目标。

补题之前先写了个工具：`knowledge/lookup.py`（74 行），在索引里按关键词定位 chunk，供人工标注 `gold_chunk_ids` 用。没有它，15 道题的 gold 只能靠翻原文猜 chunk id。

补 15 题（`knowledge/questions/m0.v2.jsonl`）：ch4–10 各 1–2 题 + 个人资料 3 题，24 个 gold 引用 / 23 个去重（`chapter7#8` 被两题共用）。

合并用 `merge_sets.py`（按 id 去重、保持输入顺序），产出 `questions/all36.v2.jsonl`（20:07）。36 题结果（20:11）：

| 配置 | Hit@5 | MRR@10 | nDCG@10 | Recall@20 | p50 |
|---|---|---|---|---|---|
| E0 裸 dense | **0.9444** | 0.7685 | 0.7434 | 0.9444 | 101ms |
| E1 BM25 | 0.7222 | 0.5927 | 0.6017 | 0.8194 | 9ms |
| E2 +RRF | 0.9167 | 0.7098 | 0.7034 | **0.9861** | 62ms |
| E3 +重排 | 0.9167 | **0.8123** | **0.7968** | 0.9861 | 2265ms |
| E4 +改写 | 0.9167 | 0.8135 | 0.7984 | 0.9722 | 2452ms |

读法：融合扩覆盖（Recall@20 +4.2pt，Hit@5 −2.8pt = 1 题），重排加深排序（MRR +10.2pt），两者都不改变 Top-5 命中。E0 领先的 1 题是噪声（34/36 vs 33/36）。

**candidate-k 20→50 实验（20:19，证伪）**：

| | Hit@5 | MRR@10 | p50 |
|---|---|---|---|
| k=20（E3） | 0.9167 | 0.8123 | 2265ms |
| k=50（E3） | 0.8889 | 0.8100 | **5602ms** |

收益为零、延迟 ×2.5。而且 **E2 也从 0.9167 掉到 0.8889**——candidate-k 同时影响召回深度，不只影响重排池。所以这个实验真正证明的是「加深召回深度整体有害」，比原假设更硬。默认保持 k=20。

## 8. 阶段七 · 把检查做进门（守卫随首次提交；20:32–20:51 补完其余三项）

### 8.1 构建期守卫

自相似度校验从"pytest 可选项"改为"构建期强制阻断"：

```
ingest_v2.py 构建末尾 → verify_embeddings() → 任一样本 < 0.999 → return 3，拒绝产出索引
```

设计要点：`batch_size=1` 重编码。单条前向不产生 padding，因此无论上游用 left 还是 right padding 的池化实现，结果都一致——**它测的是索引本身，而不是修复是否生效**。

抽样策略：首/中/尾 + 最短 5 块 + 最长 2 块（专挑最易触发 padding 的）。

**用新守卫回头查旧索引**——这是本轮方法论上最值钱的一步：

```
[verify][FAIL] book/introduction.md#9   0.3816   496 chars
[verify][FAIL] book/chapter2.md#10      0.5956  1899 chars
[verify][FAIL] book/chapter3.md#22      0.5091   726 chars
[verify] 抽样 9 条，最差自相似度 0.0508      → 6/9 失败，exit 3
```

`chapter2#10` 有 1899 字符，是**正文中段**，不是尾块。所以缺陷是系统性的，v1 那套 0.857 的基线同样不可用。（注：抽样专挑短块，有偏，只能证明"存在系统性错位"，不能读成"67% 的块坏了"。）

### 8.2 退出码分层

原来"网络崩"和"数据坏"共用一条失败路径，无法区分。改为：

| 码 | 含义 | 处置 |
|---|---|---|
| 0 | 通过 | — |
| 2 | 调用方错误（参数非法 / 上游路径缺失 / 语料清单不符） | 改命令或改配置 |
| 3 | 数据错位 | 重建索引并排查池化 |
| 4 | 环境不可用（模型未缓存 / 索引不存在） | 改环境 |

实跑验证：正常 0、上游缺失 2、v1 索引 3、索引不存在 4。

### 8.3 离线前置

`huggingface_hub` 在**导入期**读取 `HF_HUB_OFFLINE` 常量，设晚了不报错，只表现为"每次调用静默尝试联网直到超时"。

抽成 `knowledge/_offline.py`：「在用户未显式允许联网时设置离线变量」，`loader.py` 顶部第一件事导入它。首次下载模型时设 `AIDE_ALLOW_HF_NETWORK=1`。

### 8.4 断言换成读常量

第一版离线断言读 `os.environ`，但真正决定行为的是 `huggingface_hub.constants.HF_HUB_OFFLINE`：

```
先 import loader        → 常量 True
先 import hf 常量再导入  → 常量 False，而 env = 1   ← 旧断言照样绿
```

改成干净子进程 + 读常量，并给出可观测信号：`exit 10` = SDK 已加载但常量为 False（设晚了）、`exit 11` = 环境变量未设。

## 11. 事故与教训

| # | 事故 | 性质 | 教训 |
|---|---|---|---|
| 1 | pooling 与 padding 方向不匹配 | 静默缺陷 | 不报错不等于正确；自相似度是最便宜的体检 |
| 2 | 首轮把缺陷解释成"扩容代价" | 误判 | 数字下降时先验工具，再解释原因 |
| 3 | 21 题测不到 ch4–10 | 尺子不对 | 验收题集必须覆盖目标分布 |
| 4 | 报"下降 0.0952"未做显著性 | 口径错 | 21 题上 0.0952 = 2 道题，p=0.5 |
| 5 | 守卫写在 pytest 且默认跳过 | 检查失效 | 守卫要在构建路径上，失败即阻断 |
| 6 | 网络崩与数据坏共用退出码 | 不可判读 | 退出码要按处置方式分层 |
| 7 | 离线依赖 import 时序 | 设置失效 | 前置模块 + 单一实现处 |
| 8 | 断言读环境变量而非常量 | 测错对象 | 测产出物，不测输入 |

前 8 条在 M0 内闭环。第 9、10 条（勾选无载体、规格依赖成环）出现在 M1 清单阶段，已另记 `docs/status.md`。

## 12. 遗留与转交

- **扩容净效应：未测。** v1 基线带缺陷，两列不能相减。已明确改为「v2 在 36 题上的绝对水平 + 新增覆盖 + 人工抽查」，净效应交 M5 任务层回答。
- **E4 改写：保留待观察。** 36 题上 MRR 仅 +0.0012、Recall@20 −1.4pt，代价是多一次 LLM 调用。
- **分块策略：固定窗口未改。** skill 推荐结构感知切分，此处为保持单变量可比暂不改，列为后续实验。
- **candidate-k：保持 20，不做改动**（20→50 已证伪）。
- **旧项目影响：** v1 索引存在系统性错位，若线上服务仍在使用，需要重建。ADR 0002 已建议向上游提 issue。
