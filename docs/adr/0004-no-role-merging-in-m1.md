# ADR 0004：M1 不做连续同角色消息合并

- 状态：已接受
- 日期：2026-10-30
- 关联里程碑：M1（A 组第 5 条断言）

## 背景

M1 验收清单原有一条断言：

> `test_message_roles_respect_provider_constraint` —— 连续同角色消息按 provider 约束**合并**，不产生非法角色序列。

实现里没有合并逻辑，测试也只断言了角色序列合法。这是**同名不同义**：断言名保留着
"合并"的要求，实际只验证了"角色合法"，等于把规格悄悄降级而没有记录。

部分厂商（如 DeepSeek 系列）对连续同角色消息有额外要求，因此"合并"不是无意义的工程洁癖。

## 决策

**M1 不做合并**，并把断言改名为 `test_message_roles_valid_and_not_text_spliced`，
要求收敛为"角色合法 + 不出现自行拼接的对话格式"。理由三条：

1. **无法验证**。合并是否符合厂商契约，只有真实 API 能判定；`FakeProvider` 只能验
   "我们发了什么"，验不了"对方接受什么"。在 M1 用 mock 断言合并，等于自证自话。
2. **会破坏状态栏位置不变量**。状态栏是末条 `user` 消息；一旦对相邻同角色消息做合并，
   状态栏就会被并入前一条 user 消息，"末条独立消息"这条位置断言随之失效。
   而状态栏位置是 B 组与 C 组的共同前提。
3. **属于 provider 适配层职责**，不属于上下文装配纯函数。纯函数保持"给什么装什么"，
   合并这类厂商差异应在 `llm/client.py` 按目标厂商能力表处理（与 reasoning 回传同层）。

## 被否决的方案

- **在 `assemble_context` 里合并**：把厂商差异塞进纯函数，破坏可测试性，且与状态栏位置冲突。
- **保留原断言名、只在注释里说明**：正是本次要消除的"同名不同义"。

## 后果

- 正面：断言名与要求一致；规格降级有据可查。
- 负面：M1 结束时对连续同角色消息没有防御。
- 解除条件：M1 后半段实现 `llm/client.py` 时，按 provider 能力表补
  `contract` 档测试（`test_consecutive_role_merge_per_provider`，需 `AIDE_CONTRACT=1`），
  届时本 ADR 作废。
