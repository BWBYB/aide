## 一、六个页面各自对应哪条后端能力

| 页面 | 后端来源 | 为什么需要它 |
|---|---|---|
| Console 对话台 | M1 轨迹 + M2 工具事件 | 把上下文结构可视化给人看 |
| Knowledge 问答 | M0 检索门面 | 展示检索链路，而不是只给答案 |
| Memory 记忆库 | M3 存储 | 冲突要人能裁决 |
| Runs 时间线 | M4 调度 | 定时任务失败要能被看见 |
| Eval 看板 | M5 结果 | 指标要能下钻到轨迹 |
| Evolution 中心 | M6 候选与灰度 | 回滚必须人确认 |

## 二、命令

```bash
make dev           # 启动 api + web
make dev-check     # 断言前端未使用 mock 数据
```

## 三、自动检查（必须绿）

- `test_no_mock_data_in_web` —— 全部数据来自真实 API，仓库内无 fixtures 兜底
- `test_context_panel_matches_trace` —— 页面显示的 token/成本与轨迹 JSONL 逐项一致
- `test_citation_links_resolve` —— 每条引用能定位到源文件与偏移
- `test_rollback_requires_confirmation` —— 回滚按钮二次确认，且显示影响范围
- `test_keyboard_navigation` —— 主要操作可键盘完成，焦点可见

## 四、人工判断

1. **不看代码，只靠界面，你能不能讲清"这一轮发生了什么、花了多少钱"？** 讲不清说明可观测性没做到。
2. **数字和轨迹对得上吗？** 随便挑一次运行，把界面数字与 `traces/*.jsonl` 手算核对，不一致即不通过。
3. **深色模式下有没有对比度问题？** 尤其砂金/陶红两色在暗底上的可读性。
