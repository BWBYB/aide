# Harness 关键取舍

面试核心材料。每条必须三栏齐全：**动机 / 被否决方案 / 实测依据**。缺一栏不算完成。

---

## 1. 知识层用适配器桥接，不迁移旧包

- **动机**：旧 `agentbook-rag` 没有 `pyproject.toml`，只能靠 `sys.path` 注入；迁移会牵动 37 个测试与已冻结的评估基线。
- **被否决**：① 把旧包复制进新仓库（产生两份真相，评估基线对不上）；② 重写检索层（浪费已验证资产，且短期内做不出同等质量的 RRF + 重排）。
- **实测依据**：见 `docs/eval/retrieval-v2.md`。语料从 181 扩到 567 chunks 后，E3 Hit@5 由 0.8571 降至 0.7619、E4 由 0.9524 降至 0.8571，属预期内的扩容代价；E3 p50 2127ms 与 v1 的 2327ms 同量级，说明延迟由重排而非语料规模主导——这条实测数据支持"不改旧包、只换索引"的决策。

## 2. 上下文布局固定为「静态前缀 + 轨迹 + 尾部状态栏」

- **动机**：ch2 的核心结论是前缀越稳定缓存命中越高。状态栏内容每轮都变，放进前缀等于每轮让缓存整体失效。
- **被否决**：① 状态栏写进系统提示词（直观但贵）；② 每轮重排消息顺序以"优化"位置（破坏前缀）。
- **实测依据**：`test_prefix_hash_stable_across_turns` 断言 + M1 轨迹里的 `cached_tokens`。

## 3. 工具协议先于工具实现

- **动机**：ch4 要求工具通用化；MCP 是标准协议。若先写一堆工具再抽协议，MCP 必然开第二条执行路径，审批与按需发现无法做成横切能力。
- **被否决**：按 ch5 `coding-agent` 的方式直接实现 16 个工具（起手快，但后期重构成本高于收益）。
- **实测依据**：`test_mcp_tool_implements_same_protocol`。

## 4. 记忆用「卡片 + 分层」，不用纯向量堆叠

- **动机**：个人场景下"记错"比"记不住"更致命。ch3 明确要求处理冲突与遗忘。
- **被否决**：① 全量对话向量化（噪声大、无法消歧）；② 只存最新值（一次误判即不可逆）。
- **实测依据**：M3 的 L1/L2/L3 分层通过率 + 冲突用例。

## 5. 验证器优先于判官

- **动机**：`agent-evaluation` 的硬规则——能写成程序化断言的一律用断言；判官噪声大，混用会让改进曲线不可信。
- **被否决**：全部用 LLM-as-Judge（写起来快，但无法区分"真提升"与"判官偏好变化"）。
- **实测依据**：M5 报告中确定性验证任务与判官任务的比例与各自结论。

## 6. 进化只改可回滚载体

- **动机**：ch9 的四种载体里，参数更新在 3 个月周期内投入产出比最低；prompt/skill/程序可 diff、可灰度、可回滚。
- **被否决**：直接微调模型（需要数据规模与训练环境，且失败不可回滚）。
- **实测依据**：M6 的灰度记录与回滚前后指标。

## 7. 单机优先，外部依赖最小化

- **动机**：SQLite + 本地文件足以跑通全链路；引入 Postgres/Redis/K8s 会让"能跑通"变成"能部署"，但拖垮进度。
- **被否决**：为"看起来生产级"上分布式组件（面试时讲不出为什么用）。
- **实测依据**：整条链路在一台 Mac 上可复现，无外部服务依赖。

## 8. 评估分两层，绝不合成一个数字

- **动机**：M0 量检索层（Hit@5 / MRR / nDCG），M5 量任务层（pass@1 / Pass^3 / 成本 / P95）。检索分高不代表任务成功。
- **被否决**：用一个"综合分"汇报（无法定位问题出在检索还是编排）。
- **实测依据**：`docs/eval/retrieval-v2.md` 与 `docs/eval/task-baseline.md` 分开成文。

## 9. 有意不做多 Agent、语音、Computer Use、后训练

- **动机**：ch10 论断"多 Agent 的每个设计决策都能在单 Agent 三要素中找到对应"——应先证明单 Agent 不足。语音/GUI 需要额外模型能力；后训练投入产出比最低。
- **被否决**：全都做一点（广度好看，但每一层都没数据）。
- **实测依据**：M5 若显示单 Agent 在特定任务上明显不足，再单独立项评估多 Agent。
